## 0. 路线图总览

| 里程碑 | 范围 | 目标版本 | 时间口径 | 性质 |
|--------|------|----------|----------|------|
| **M0 — Hotfix** | 5 项安全/成本硬伤 | `0.23.2-post`（hotfix，不进列车） | 立即，1–2 天 | 一行/几行修复，止血 |
| **M1 — 0.23.2 补丁** | 8 项正确性与体验补完 | `0.23.2.1`（patch） | 本周 | 补完"可信闭环"未验收到的缺口 |
| **M2 — 0.23.3** | 契约/版本债 + 画布并发加固 + 跨版本规划项 | `0.23.3` | 进版本列车 | 偿还架构债，与画布 Skill 同期 |
| **M3 — 0.24.0+** | 长期架构演进 | `0.24.0`+ | 远期 | 数据完整性、可维护性、体验打磨 |

**决策原则**：
1. **先止血再治本最后还债**——M0 不等任何版本排期，安全/成本硬伤立即合并。
2. **同类问题专题化**——画布并发类（triggerRun/save/backfill/reloadCanvas/finalizeRun）作为一个连贯专题，不拆散。
3. **契约债分模块推进**——`@ApiResponse` 补全成本最高，按模块分批，不一次性铺开。
4. **版本基线一次性对齐**——Node/TS/Next/version 在 M2 发版时统一，避免反复。

**责任人/状态字段说明**：`负责人` 留空待分配；`状态` = 待启动 / 进行中 / 待验收 / 已完成 / 阻塞。每项含 `验收标准` 与 `风险`。

## 附录 A：画布并发加固专题（M0-5 + M1-1 + M1-3 + M1-4）

这四项是同一类"检查-后-写非原子竞态"在画布的不同面，**建议作为一个连贯 PR 链由同一人推进**，避免分散修复引入不一致：

```
M0-5  ✅ 部分唯一索引 + triggerRun/business-action 事务化 + 23505 捕获（hotfix 已完成）
  └─ M1-4   ✅ triggerRun SELECT FOR UPDATE on canvas（fix/0.23.2.1 已完成）
       └─ M1-1  ✅ save/backfill 同一 canvas advisory lock（双侧同锁，已完成）
            └─ M1-3  ✅ finalizeRun CAS 终结（三终态，已完成）
                 └─ M1-2  ✅ reloadCanvas 字段级 merge（保留本地 position/prompt，已完成）
```

**专题验收**：四项已实现（后端 typecheck + 95/95 单测通过）。合并前仍需在真实 DB 跑一次"并发触发 run + 生成期间自动保存 + 多 task 并发完成"端到端压测，确认 ① 不产生重复 run ② results 不丢 ③ run 恰好终结一次、计数准确、三种终态正确 ④ 生成期间拖动节点完成后位置不回弹。
