# 0.23.2 研发规格任务列表

版本：`0.23.2`
日期：`2026-07-07`
状态：已封版，本文作为验收基线归档
主线：画布可信闭环验收版

> 封版结果见 [0.23.2封版说明.md](./0.23.2封版说明.md)。本文保留为 `0.23.2` 的研发范围、门禁和 No-Go 基线。

## 1. 版本目标

`0.23.2` 是**验收版**，不是从零开发版。资产闭环、上传闭环、快速生成主体已在 `0.23.1` 期间落地，节点生成历史部分落地。因此 `0.23.2` 的真实工作量是：

1. 补齐一个真开发缺口（节点生成历史并发写保护）。
2. 补齐验收证据（后端单测、E2E、资产来源展示与筛选）。
3. 修订几处文档与代码不一致口径。
4. 走通六步可信闭环验收链路。

封版成功标准（见 `第 6 节 封版门禁`）：把画布"生成/上传 -> 历史 -> 资产 -> 预览下载 -> 回源 -> 刷新不丢"这条链路做成可判定、有测试证据的闭环。

## 2. 优先级口径统一

本版本此前存在两套优先级编号（`0.23版本计划.md` 四段清单 vs `VERSION_PLAN.md` 六项表）。

**本文为 `0.23.2` 研发优先级的唯一真相源**，其余文档只作概述。统一口径如下：

| 优先级 | 范围 | 状态 | 本版本主要工作 |
|--------|------|------|----------------|
| P0 | 节点生成历史并发写保护 | 部分落地 | 补事务/锁，防止并发 append 丢结果（唯一真开发缺口） |
| P1 | 画布资产闭环验收 | 已基本落地 | 补来源类型展示文案、筛选、回源 E2E |
| P2 | 画布上传闭环验收 | 已基本落地 | 补失败文案、大小/类型测试、刷新验收 |
| P3 | 画布生成历史验收 | 部分落地 | 补 node-result 单测与历史面板 E2E |
| P4 | 最小快速生成验收 | 已基本落地 | 明确结果默认是否进历史/资产，补 E2E |
| P5 | AI-first 回归（可选） | 未开始 | 长篇分块、字段漂移、真实 API 失败样本回归（见 4.6） |

说明：

- P4「AI-first 回归」在 `VERSION_PLAN.md` 曾被列为必做但无验收标准。本文将其定为**可选项**，仅在补齐验收标准（见 4.6）后才可升级为必做。
- 全量 8 个画布 Skill、画布 AI 对话代理、角色/场景端口连线、合成导出节点均**不在 0.23.2**，进入 `0.23.3` / `0.24.0` / `0.25.0`。

## 3. 不做范围

- 不做多人实时协作。
- 不做复杂分支版本合并。
- 不做完整时间线剪辑工具。
- 不做画布 Skill 对话代理、角色/场景端口连线、合成导出节点（进入 `0.23.3`）。
- 不做完整 8 个 Skill（`delete_nodes / create_edge / delete_edge / generate / save_to_assets` 等进入 `0.24.0` / `0.25.0`）。
- 不新增独立原型页或复杂资产版本合并页。
- 不做画布直接覆盖短剧源数据（`DEBT-11` 定论：0.23.2 只做资产和来源追溯）。

## 4. 研发任务清单

### R232-00 版本范围与验收基线

优先级：P0

目标：明确 0.23.2 是验收版，不扩画布 Agent 范围。

任务：

1. 冻结本文优先级为研发口径，`0.23版本计划.md` / `VERSION_PLAN.md` 的优先级表只作概述。
2. 所有 0.23.3 及以后能力入口不进入 0.23.2 交付验收。
3. 建立六步验收链路清单，作为封版检查表（见第 6 节）。

验收：

- 研发与测试对 0.23.2 范围与优先级无口径分歧。

### R232-01 节点生成历史并发写保护

优先级：P0（唯一真开发缺口）

现状：`CanvasNodeResultService` 的 `appendResult / selectResult / markAssetId` 均为对 `canvasNodes.dataJson` 的"读-改-写"，无事务或行锁（同模块 `canvas-save / canvas-run` 已用事务，唯独此处未用）。两次并发 `appendResult` 会 last-write-wins 覆盖，直接违反需求「并发生成时不得丢失结果」。

路径：

- `apps/backend/src/modules/canvas/canvas-node-result.service.ts`

任务：

1. 为 `appendResult / selectResult / markAssetId` 的读-改-写包 transaction。
2. 采用行锁（`SELECT ... FOR UPDATE`）或乐观锁版本号，二选一：
   - 行锁：事务内先锁定目标 `canvas_nodes` 行，再读-改-写。
   - 乐观锁：`data_json` 或节点行增加版本号，写入时校验版本，冲突则重试。
3. 保留「最多 20 条结果」的截断逻辑，确保并发下不越界、不丢失最新结果。
4. `current_result_id` 在并发下保持一致，不出现指向已被截断结果的悬挂引用。

验收：

- 并发两次 `appendResult` 后，两条结果都在，`current_result_id` 指向有效结果。
- 并发 append 与 select 交叉执行不产生脏数据。
- 20 条上限在并发下仍成立，且淘汰的是最旧结果。

### R232-02 画布资产闭环验收

优先级：P1（已基本落地，补验收）

现状：`CanvasAssetService`、`POST /api/v1/canvases/:id/assets`、`assets.source_ref/source_path`、幂等（canvas_id+node_id+result_id）、回写 `results[].asset_id` 均已实现。四种来源类型（`canvas_upload / canvas_generation / canvas_export / canvas_history`）在应用层写入，但 `source_type` 仅 `varchar(50)`、无 DB 级枚举约束。

任务：

1. 资产库对四种画布来源类型有正确展示文案与来源标识。
2. 资产库支持按画布来源类型筛选。
3. 资产详情或列表支持「打开来源画布」并定位相关节点。
4. `source_type` 取值收敛：在应用层建立单一来源类型常量/枚举，避免各处硬编码字符串漂移；DB 级约束可后续评估，本版本至少保证代码层唯一来源。

验收：

- 画布结果保存后资产库可见，来源类型文案正确。
- 可按来源类型筛选出画布产物。
- 从资产可回到来源画布并定位节点。
- 刷新后资产来源和节点 `asset_id` 状态不丢失。

### R232-03 画布上传闭环验收

优先级：P2（已基本落地，补验收）

现状：`CanvasUploadService`、`POST /api/v1/canvases/:id/uploads`、前端 `CanvasUploadDialog` 已实现。大小限制为**分档**：图片 30MB / 视频 200MB / 音频 100MB，顶层硬上限 200MB。`save_to_assets` 已支持。

任务：

1. 上传失败文案覆盖：超大小、类型不允许、网络失败、后端拒绝。
2. 大小/类型测试覆盖分档上限（图片 30MB、视频 200MB、音频 100MB）和白名单边界。
3. 上传后刷新验收：节点仍在；勾选保存资产后资产库有对应记录。
4. 文档与文案统一为分档口径，不再笼统写「200MB 限制」。

验收：

- 上传真实文件后画布出现对应类型节点（image / video-asset / audio）。
- 刷新后上传节点仍存在。
- 勾选保存资产后资产库出现对应资产。
- 超限或非法类型有可解释失败文案，不静默失败。

### R232-04 画布生成历史验收

优先级：P3（部分落地，补测试）

现状：`CanvasNodeResultService`、前端 `NodeResultHistoryPanel`、20 条上限、`current_result_id`、切换、下载、保存资产均已实现。缺 `canvas-node-result.service.test.ts` 与历史面板 E2E。并发保护见 R232-01。

任务：

1. 新增 `canvas-node-result.service.test.ts`，覆盖：追加、20 条截断、选择当前结果、保存资产回写、并发写保护（依赖 R232-01）。
2. 历史面板 E2E：连续生成多次可见多条历史、切换预览、刷新后当前选择保持、下载、保存资产。

验收：

- 同一节点连续生成多次后可见多条历史。
- 选择历史后节点预览切换，刷新后保持。
- 历史结果可下载、可保存资产。
- 并发写保护测试通过。

### R232-05 最小快速生成验收

优先级：P4（已基本落地，补口径与测试）

现状：`useCanvasQuickGenerate`、`QuickGenerateDialog` 已实现；business-action 支持 `output_mode=insert_new_node`、`position_x/position_y`；新节点写入 `references`。

任务：

1. 明确产品口径：**快速生成结果默认进入节点历史，不自动进入资产；需要用户显式保存资产**，并在文档与实现中一致。
2. 空白右键快速生成、单节点右键快速生成两个入口验收。
3. 新节点位置：空白生成插入视野中心，单节点生成插入来源节点右侧。
4. 新节点 `references` 记录来源节点或来源资产。

验收：

- 空白快速生成后画布出现结果节点。
- 单节点快速生成后新节点包含来源引用。
- 生成结果默认进入节点历史，不自动进入资产；用户可从历史面板或节点菜单显式保存资产。
- 刷新后新节点和当前结果仍存在。

## 6. 封版门禁

`0.23.2` 只有满足下面全部，才能封版：

1. 六步验收链路可跑通：生成或上传结果 -> 在节点历史看到并可切换 -> 在资产库找到 -> 预览或下载 -> 打开来源回到画布 -> 刷新后结果/来源/运行状态不丢。
2. 节点生成历史并发写保护已实现（R232-01），并发 append 不丢结果。
3. `canvas-node-result.service.test.ts` 存在且通过，覆盖并发写保护。
4. E2E `06-node-result-history` 与 `07-minimum-quick-generate` 存在且通过。
5. 资产库四种画布来源类型有正确展示文案与筛选，可回源。
6. 上传失败文案、分档大小/类型校验有测试证据。
7. 快速生成口径已定并实现一致：默认进入节点历史，不自动进入资产，资产保存由用户显式触发。
8. 构建、类型、lint 通过。

## 7. 封版 No-Go

出现以下任一情况，`0.23.2` 不允许封版：

1. 并发生成仍会丢结果或覆盖历史。
2. 缺 `canvas-node-result.service.test.ts` 或 E2E 06/07。
3. 资产库无法区分或筛选四种画布来源类型。
4. 资产无法回到来源画布。
5. 刷新后节点结果、当前选择、资产状态丢失。
6. 上传超限或非法类型静默失败。
7. 快速生成默认进入节点历史、不自动进入资产的行为与文档不一致。

## 9. 交付判定

`0.23.2` 不按「补了多少画布功能」判定，而按可信闭环判定：

`生成或上传 -> 节点历史 -> 资产库 -> 预览下载 -> 回源画布 -> 刷新不丢`

这条链路只要断在任何一环，或并发生成会丢结果，`0.23.2` 就不能封版。
