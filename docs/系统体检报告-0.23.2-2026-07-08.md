## 1. 总体架构评估

### 1.1 仓库形态与分层

小窗是一个 **pnpm/npm workspaces 单仓**，`apps/*` + `packages/*` 共 7 个工作区：

```
apps/
  backend/   NestJS 11 + Fastify + Drizzle + BullMQ + Redis + PG   （业务中枢 + worker）
  web/       Next.js 15 App Router + React 19 + Zustand + @xyflow    （前台创作端）
  admin/     Next.js 16 App Router + React 19                       （后台只读管理端）
  data/      数据/种子
packages/
  contracts/      OpenAPI 契约（openapi.json → generated.ts + 手写 shared.ts）
  canvas-shared/  画布节点定义/PortType/Prompt 模板（前后端真共享）
  ui/             共享 UI 库（当前为空壳）
```

分层意图是正确的：**前台/后台 → 契约层 → 后端**，画布逻辑通过 `canvas-shared` 在前后端间复用，异步任务通过 `worker` 独立进程承接。这条主链路在代码里确实落下来了（`canvas-shared` 有 25+ 前端引用 + 后端 dist 引用，是三个包里唯一名副其实的共享包）。

### 1.2 架构优点

- **关注点分离到位**：HTTP 入口（`main.ts`/`app.factory.ts`）与 worker 入口（`worker-main.ts`）解耦；worker 用 `ApplicationContext` 复用模块，`workerId` 含 pid+随机串避免多实例冲突，优雅关停走四态 readiness 机（`worker-main.ts:208-238`）。
- **契约驱动意图清晰**：`generate:contracts` 串起"后端导出 OpenAPI → `openapi-typescript` 生成 `generated.ts` → tsc 出 dist"，README 明确"不放 DB/业务/鉴权"。
- **边界守卫工程化**：`tools/check-v2-boundaries.mjs` 用 4 类导入规则 + 6 个 legacy 路径禁回归 + 3 套"路由处理器必须只剩代理壳"的精确文件集规则（`exactFileSetRules:60-85`），思路非常对——防止前端混入 DB 直连、防止 legacy 复活。
- **运行时编排规范**：`docker-compose.runtime.yml` 含 postgres/redis/minio/minio-init/backend/worker，全服务带 healthcheck，worker 健康检查读 `/tmp/task-worker-ready.json`（`docker-compose.runtime.yml:88-92`）——精细到 worker 就绪信号。
- **版本治理有"列车"**：`docs/VERSION_PLAN.md` 维护 0.21→1.0 的版本线、当前版差异、下一版方向，RELEASES/ 逐版留档，封版证据可复查。

### 1.3 架构问题

| 问题 | 位置 | 说明 |
|------|------|------|
| **契约层"名不副实"** | `packages/contracts/openapi.json` + 各 controller | 157/157 operations 无响应 schema；后端全仓 0 个 `@ApiResponse`。`generated.ts` 的 `paths/operations` 三端零引用，真实类型源是手写 `shared.ts`（686 行）。前后端字段漂移无编译期保障——这是全栈 TS 系统最该修的契约债。 |
| **共享 UI 库是空壳** | `packages/ui/src/index.ts:1-2` | 仅一行 `export {};`，零实现，apps 全无引用。web 用自己的 `components/ui/`，admin 用 `admin-kit.tsx`，两套设计系统分叉，`@xiaochuang/ui` 制造"已有共享设计系统"的错觉。 |
| **版本基线碎片化** | `.nvmrc`/各 `package.json` | `.nvmrc`=22、`@types/node` backend/web=25、admin=^20；TS 6.0.2(backend/web) vs ^5(admin)；Next 16(admin) vs 15(web)；所有 `package.json` version 冻在 0.22.0 但已发 0.23.2。`audit-v2-completion.mjs:21-39` 自己用 node@22 重 exec 自己——**作者自证 Node 25 有问题、强制降回 22**，开发/CI 版本分裂。 |
| **无 root `engines` 字段** | `package.json` | 不强制 Node 版本，靠 `.nvmrc` + CI 软约束。 |

### 1.4 架构总体评分：7.5 / 10

骨架与意图是 8.5 分水准，但"契约半套 + UI 空壳 + 版本碎片"三处给架构图制造了"比实际更完整"的错觉，拉到 7.5。

## 2. 后端逐模块推敲

### 2.1 启动与装配（main / app.module / app.factory / worker）

**优点**：`app.factory.ts:28-31` FastifyAdapter 配置合理；`:38-48` 自定义 multipart parser 以 buffer 透传避免双重缓冲；`:51-55` 本地静态路由按 `STORAGE_DRIVER` 条件注册、生产强制 s3；`worker-main.ts` 优雅关停四态机。

**问题**：`main.ts:17` `void bootstrap()` 未捕获 promise rejection——端口占用等启动失败会以 unhandledRejection 退出而非可读栈，建议 `.catch()`。

### 2.2 环境配置（config/env.ts）

**优点（突出）**：`env.ts:51-183` zod `superRefine` 校验极严格——生产禁用 `DEV_AUTH_BYPASS`/`E2E_AUTH_MOCK`/`SMS_PROVIDER=console`/`DRAMA_AI_FIRST_LOCAL_RULE_FALLBACK`，生产强制 `STORAGE_DRIVER=s3`+`STORAGE_PUBLIC_BASE_URL`，`AI_CONFIG_ENCRYPTION_KEY` 生产必填且 ≥16 字符，`VIDU_WEBHOOK_SECRET` ≥16 字符且与 `WEBHOOK_BASE_URL` 成对，`DEV_AUTH_CODE` 必须 6 位。`:49` `.passthrough()` 保留未知 env。

### 2.3 认证模块（modules/auth/）

**优点**：`password.ts:5-9` scrypt + 16 字节 salt；`verifyPassword` 用 `timingSafeEqual` 防时序攻击；session token 32 字节随机；`auth.service.ts:85-106` session 校验三条件（hash 比对 + `gt(expiresAt)` + `isNull(revokedAt)`）；`:113-121` lastSeenAt 60s 节流；`auth-registration.service.ts:19-22` SMS 三重限流（60s 重发 / 5 次每小时 / 5 次尝试）；`auth-dev.ts:6-9` 生产硬编码 `return false`；`auth.controller.ts` `next` 参数强制 `startsWith('/')` 防开放重定向（且测试 `auth.controller.test.ts:60-80` 覆盖）；`auth.service.ts:157` cookie `httpOnly`+`sameSite:lax`+生产 `secure`。

**问题（中）**：`auth-registration.service.ts:99-166` `registerUser` 中"验证码校验 → 唯一性查重 → 插入用户 → markCodeUsed"非事务。两个并发注册用同一手机号都通过查重后只有一个插入成功，但**验证码已被消费**——失败方需重新获取验证码。建议查重+插入包进事务并依赖唯一约束兜底。

### 2.4 画布模块（modules/canvas/）★ 0.23.2 主线

这是本次封版主线。**节点结果并发写保护的核心是到位的**，但运行编排层有真实竞态。

#### 2.4.1 节点结果并发写保护（到位，正面范例）

- `canvas-node-result.service.ts:67-120` `appendResult`、`:136-166` `selectResult`、`:168-194` `markAssetId` 三者均在 `db.transaction` 内 `SELECT ... FOR UPDATE`（`:73/:142/:173`），行锁串行化。
- `:104` results 数组 `.slice(0, 20)` 上限防膨胀；`:181-184` `markAssetId` 后校验 `current_result_id` 仍指向存在结果，避免悬空。
- `canvas-node-result.service.test.ts:177-209` 有并发 append+append、append+select 交错测试。
- `canvas-asset.service.ts:61-70` 已有 asset_id 的 result 复用现有 asset 而非重复插入。

#### 2.4.2 triggerRun TOCTOU 竞态（高）

- `canvas-run.service.ts:38-43` 活跃 run 检查与 `:56-86` 插入新 run **不在同一事务、无锁**。`schema.ts:1114-1115` `canvas_runs` 仅有 `idx_canvas_runs_canvas_id`/`idx_canvas_runs_status` 普通索引，**无 `(canvas_id, status) WHERE status IN ('pending','running')` 部分唯一索引**兜底。两个并发 `POST /canvases/:id/run` 都通过检查 → 都插入 run+tasks，同一画布产生两个并行 run，tasks 互相干扰。
- `canvas-run.service.ts:90-92` `void this.orchestrator.startRun(...).catch(...)` fire-and-forget：若 orchestrator 启动失败，run 已落库为 pending 但无 task 入队，**run 永远卡 pending**；而 `worker.ts` recover 只处理 `tasks` 表的 drama tasks，**不处理 `canvas_tasks`**，canvas run 无超时清理。
- 建议：triggerRun 包进事务 + `SELECT FOR UPDATE` on canvas row，或加部分唯一索引；失败时回滚 run 状态 + 加 run 超时检测。

#### 2.4.3 全量 save 与 run backfill 数据丢失（高）

- `canvas-save.service.ts:86-90` 全量保存是 `tx.delete(canvasNodes).where(eq(canvasId, id))` + `tx.delete(canvasEdges)` + 重新 INSERT。前端 3s 防抖自动保存（`useDebouncedSave.ts`）在 run 进行中持续触发，**客户端 save payload 里的 node data 不含 run 正在 backfill 的 results**。
- `canvas-result-backfill.service.ts:39-55` 的 `appendResult` 在 `FOR UPDATE` 行锁内更新目标 node 的 dataJson。若 `appendResult` 先提交（node 已含 results），随后 save 的 `DELETE canvasNodes` 整行删除并重插客户端版本（无 results）→ **刚生成的 results 被覆盖丢失**。
- 建议：save 时对 canvas 加 advisory lock，或拒绝在 running run 期间全量保存，或 save 改为字段级 upsert 而非整行删插。

#### 2.4.4 finalizeRun 并发可能永不终结（中）

- `canvas-run-orchestrator.service.ts:111-146` `finalizeRun` 读全部 tasks → 算统计 → 更新 run status，**三步非原子**。`processor.ts:70` 每个 task 完成都调 `onTaskSettled`，多个并发调用可能各自看到对方还没完成的 task 而都 `if (pending>0) return`，run 永不终结。
- 建议：用 `UPDATE ... WHERE status='running'` 的 CAS 终结，或对 run 行加锁。

#### 2.4.5 画布接口 IDOR（中高，已复核）

- `canvas-features.controller.ts:46-60` `listResults` 与 `selectResult` 均未注入 `@CurrentUser()`、未调 `requireOwnedCanvas`。控制器仅 `@UseGuards(SessionAuthGuard)`（登录即可），服务签名 `listResults(id, nodeId)` / `selectResult(id, nodeId, resultId)` 不含 userId，**无法校验请求者拥有该画布**。对比同控制器 `upload:31`、`saveAsset:42` 都传了 `user.id`。
- 后果：任意登录用户可读/选任意画布节点结果，`selectResult` 还会改写 `current_result_id`。建议补 `requireOwnedCanvas(id, user.id)`。

#### 2.4.6 其他画布发现

- 优点：`canvas-upload.service.ts:19-44` 上传策略表按 image/video/audio 区分 maxBytes+mimeTypes+extensions，`:246-255` 双重大小校验，`:50-54` 文件名 sanitize；`canvas-save.service.ts:60-61` 节点/边数量上限（250/500）+ node.type 白名单；`canvas-execution.service.ts:88-100` `claimTask` 用 CAS `WHERE id=? AND status=?` 防双 worker 抢同一 task。
- 问题：`canvas-run.service.ts:118` `JSON.parse(task.resultJson)` 无 try/catch（其他文件有 `safeJsonParse` helper，此处漏用），损坏 resultJson 会让 `getRunStatus` 500；`:149` `eta_seconds: running ? 60 : undefined` 硬编码。

### 2.6 任务与队列（tasks/ + queue/）

**优点**：`task-execution.service.ts:135-150` `claimQueuedTask` 用 CAS `WHERE status='queued' AND deleted_at IS NULL RETURNING id` 原子抢占；`:152-157` `canRecoverRunningTask` 按 `lockExpiresAt`（10 分钟 TTL）判断过期锁可被接管；`:9` `MAX_RETRY_ATTEMPTS=7` 达上限转 `dead_letter`；`task-queue.shared.ts:15-30` BullMQ 3 次尝试+指数退避（10s+20% jitter）+ removeOnComplete/Fail；`task-queue.service.ts:41-47` enqueue 前查 existing job 复用 jobId（幂等）；`task-worker.processor.ts:74-77` 终态失败抛 `UnrecoverableError` 终止重试。

**0.23.2 task error semantics 硬化（commit d7ab657）**：① `task-domain.registry.ts:125-145` 未知 `domainTable` 不再静默返回 `'unknown'`，而是 `markUnsupportedDomainTask` 写 `status='failed', errorKind='unsupported_domain'`，避免孤儿任务卡死；② `storyboard-tts-task.handler.ts` 把硬编码 `errorKind:'provider'` 改为 `inferErrorKind(message)`，引入 `task-domain-utils.ts:53-76` 的错误分类（network/quota/moderation/validation/provider/canceled）。这是一次实打实的质量提升。

**问题（中高）**：
- **视频轮询 50 分钟 vs 锁 10 分钟不匹配**（见第 0 节问题 4）。`videos.service.ts:467` `for (let i<300) setTimeout(10_000)` ≈ 50 分钟，`task-execution.service.ts:8` `LOCK_TTL_MS = 10 分钟`，且与 `videos.service.ts:378` `AbortSignal.timeout(600_000)` 恰好相等。视频任务接近超时时锁恰好过期 → recover worker 抢走重跑 → **重复生成扣费**。建议 lock TTL > 最长 provider 超时（如 15 分钟）。
- `refreshTaskLock:116-127` 无条件 UPDATE 刷新锁，未校验 `lockedBy === workerId`，并发下可能覆盖他 worker 的锁。建议加 `WHERE lockedBy = workerId`。
- **两套重试计数不对齐**：BullMQ `attempts:3` vs 应用层 `MAX_RETRY_ATTEMPTS:7`。BullMQ job 失败 3 次进 failed set（保留 7 天），但 tasks 表 `attemptCount` 仅到 3 未达 7 不标 dead_letter → 任务陷入"既不在 BullMQ 活跃队列、也未达死信条件"的僵死状态，只能靠 recover 重新入队。

### 5.2 契约层（packages/contracts/）★ 核心债

**致命问题——契约只做到"半套"**（已复核）：
- `openapi.json` 统计：**116 paths / 157 operations，157 个操作全部没有 JSON 响应 schema**；`components/schemas` 仅 **10 个且全是输入 DTO**（`SessionCreateDto`/`AiRuntimeInputDto` 等）。

## 8. 总评

小窗 0.23.2 是一个**工程态度认真、治理脚手架齐全、封版流程诚实**的系统。它在 SSRF 防护、CAS 任务抢占、AES-GCM 密钥加密、AI-first 分块与失败样本归一化、画布节点结果并发写保护（事务+行锁）、边界守卫脚本、运行时编排等处都体现了专业水准；0.23.2 封版目标达成度高，验收证据可复查、已知风险诚实记录进入下一版。

但它与"生产级稳健"之间有**明确且可补的差距**，集中在三类：

1. **安全鉴权覆盖不均**——uploads 匿名上传、canvas 节点结果 IDOR，都是一行/几行即可修复的低悬果，却被遗漏。
2. **"检查-后-写"非原子竞态普遍**——triggerRun、finalizeRun、webhook 幂等、proposal apply、save/backfill 全是同一类问题，且视频轮询 50 分钟 vs 锁 10 分钟的不匹配会直接导致重复扣费。
3. **契约与版本基线"名实不符"**——OpenAPI 只做到"半套"（157/157 无响应 schema，真实类型源是手写 shared.ts），`@xiaochuang/ui` 空壳，版本号三处脱节、Node/TS/Next 版本碎片化。

这三类问题都不需要推翻架构，而是需要"在现有扎实骨架上把正确性细节补齐"。建议按 P0→P1→P2 顺序推进：P0 的 5 项是安全与成本硬伤应立即修，P1 的 8 项是 0.23.2 自身"可信闭环"的补完，P2 的 13 项偿还契约与版本债、进入 0.23.3。

> 一句话：**小窗 0.23.2 的骨架是 8 分、契约与边界是 7 分、关键正确性细节是 6 分，综合 6.8——这是一个"值得继续长大"的底座，前提是把鉴权与并发两类的"最后一公里"补上。**
